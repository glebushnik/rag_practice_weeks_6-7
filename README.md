# Практика: GraphRAG для поддержки SaaS-инцидентов

Я подготовил эту практику, чтобы ты собрал систему, которая помогает инженеру поддержки разобраться в инциденте по внутренним документам. В реальной работе ответ редко лежит в одном абзаце: симптом описан в одном месте, зависимость сервисов — в другом, а порядок проверки — в третьем. Здесь ты попробуешь соединить эти сведения и проверишь, приносит ли граф пользу по сравнению с обычным RAG.

Компания **CloudLine** и все документы в этой практике вымышлены. CloudLine продаёт B2B-сервис для работы с клиентскими заявками. У него есть авторизация, платные возможности, уведомления, вебхуки и экспорт данных. Никаких внешних API и настоящих клиентских данных для работы не требуется.

## Что лежит в репозитории

- [`data/knowledge_base/`](data/knowledge_base/) — внутренняя база CloudLine: Markdown, DOCX, PDF и CSV. Там есть описания сервисов, инструкции, отчёты об инцидентах и журнал событий. У каждого источника есть ID: сохраняй его при обработке, чтобы потом можно было проверить ответ.
- [`evaluation/questions.jsonl`](evaluation/questions.jsonl) — вопросы для проверки. В файле есть вопросы, на которые в документах ответа нет.
- [`practice_graph_rag.ipynb`](practice_graph_rag.ipynb) — каркас работы в Colab. Я оставил этапы и пустые ячейки; реализацию ты пишешь сам.

После публикации репозитория ноутбук можно открыть [прямо в Colab](https://colab.research.google.com/github/glebushnik/rag_practice_weeks_6-7/blob/main/practice_graph_rag.ipynb).

## Задача

Представь, что инженер поддержки получает вопрос вроде «Оплата прошла, но платная функция не открылась — где искать причину?». Твоя система должна вернуть короткий ответ, указать документы, на которых он основан, и честно сказать, когда сведений не хватает.

Я жду от тебя **две версии решения** в одном ноутбуке:

1. **Базовый RAG.** Прочитай документы разных форматов, подготовь их для поиска, найди подходящие фрагменты и дай локальной языковой модели контекст для ответа.
2. **GraphRAG.** Построй небольшой граф знаний по тем же документам и используй связи между сущностями при поиске доказательств для ответа.

Покажи, какие документы и связи привели к ответу. Любое утверждение об устройстве CloudLine должно подтверждаться исходным документом. Если данных нет, ответ должен прямо говорить об этом. Граф тоже должен быть проверяемым: у созданных связей должен сохраняться источник.

Для управления многошаговым процессом используй **LangGraph**. Мне важно увидеть состояние выполнения, выбор следующего шага и ограничение числа шагов. Используй **LangChain** для работы с документами, моделью и/или retrieval-компонентами. Выбор конкретных узлов, типов сущностей, способа извлечения связей и поиска я оставляю тебе.

## Ограничения

- Всё должно запускаться в **Google Colab** без платного LLM API. Языковая модель запускается в самом ноутбуке.
- Работай с данным корпусом; добавлять вымышленные сведения в базу знаний нельзя. Все документы текстовые, поэтому OCR в этой версии практики не нужен.
- Не используй ответы модели как источник фактов о CloudLine.
- Размер графа и индекса должен оставаться небольшим, чтобы ноутбук можно было пересоздать с нуля за одну учебную сессию.
- Для сравнения двух версий используй один и тот же набор вопросов, одну локальную LLM, сопоставимый объём контекста и одинаковые правила оценки.

Подходящие небольшие модели для эксперимента: [Qwen3-0.6B](https://huggingface.co/Qwen/Qwen3-0.6B) и [Qwen2.5-1.5B-Instruct](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct). Для многоязычного поиска можно рассмотреть [paraphrase-multilingual-MiniLM-L12-v2](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2). Это варианты, а не обязательная комбинация. Доступность GPU в бесплатном Colab [меняется](https://research.google.com/colaboratory/faq.html); если выберешь другую локальную модель, объясни выбор и зафиксируй условия запуска.

## Как я предлагаю оценивать результат

В [`evaluation/questions.jsonl`](evaluation/questions.jsonl) я оставил вопросы **без ответов и без ID нужных документов**. Для самостоятельной проверки разметь небольшой собственный набор: вопрос, ожидаемые факты, документы-основания и допустимость отказа от ответа. После этого прогони обе версии системы на одинаковых вопросах. Отдельный эталонный набор преподавателя нужен для итоговой проверки и не входит в раздачу ученикам.

Считай и покажи хотя бы эти показатели:

| Показатель | Что считать |
| --- | --- |
| **Evidence Recall@5** | Доля нужных документов, попавших в первые пять **уникальных ID источников**. Считается по вопросам с ответом. |
| **Покрытие фактов** | Доля ожидаемых фактов, которые присутствуют в ответе и подтверждаются документами. |
| **Точность ссылок** | Доля указанных в ответе документов, которые действительно подтверждают соседнее утверждение. |
| **Корректный отказ** | Доля вопросов без ответа, на которые система не выдумала решение. |
| **Проверка связей** | Доля проверенных вручную связей графа, которые подтверждаются указанным документом. Возьми не меньше десяти связей. |
| **Время и шаги** | Среднее время ответа и число шагов LangGraph на вопрос. |

Для первых четырёх показателей можно использовать ручную разметку: корпус маленький, а такая проверка помогает увидеть ошибки поиска и генерации отдельно. Объясни хотя бы **два случая**, где версии дали разные результаты. Улучшение GraphRAG по каждой метрике не является обязательным: мне важнее честное сравнение и разбор причины.
